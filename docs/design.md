# 业务设计与一致性边界

## Channel 要解决的问题

平台账号、平台会话、Multica 任务单、模型执行是四种不同身份。Channel 保留它们之间的映射，避免把“请求接收成功”“任务创建成功”“模型执行完成”“工作台采用结果”混成一个状态。

每个生产者有独立来源凭据。账号身份由来源工作台后端从当前登录账号取得；浏览器不能借用其他来源的凭据。小红书还将工作台用户 ID 纳入账号身份。来源凭据有该来源内的账号访问能力，必须保存在可信后端。

## 什么时候追加到同一张任务单

| 业务 | 推荐归并 | 条件 |
|---|---|---|
| 客服连续沟通 | conversation | 相同来源、账号、客户会话、业务类别和路由版本 |
| 同一客户同时处理两笔订单 | conversation + context.business_key | 使用不同订单号分支，避免售后信息混入另一笔订单 |
| 对同一商品连续分析价格、评价和补充图片 | topic | `context.topic_id` 使用稳定商品 ID |
| 对同一帖子分批分析评论和追加结论 | topic | 相同内容主题与业务类别；需合并的类别配置应保持一致 |
| 一次性问题、无可靠会话标识 | message | 每条独立建单 |
| 明确回复一条旧消息 | reply_to | 仅同来源、同账号、同会话、同业务事项、同类别和路由版本 |
| 主动切换话题 | new_task | 显式新建，不能同时指定 reply_to 或 thread_id |

归并键包含来源、账号、类别、规则 ID/版本、目标 agent/项目和业务范围。不会仅根据昵称、相似正文或模型猜测合并任务。相同会话可用 `business_key` 切分订单、商品或业务事项。不同平台的两个“同名客户”不会自动归为同一人。

明确回复优先定位原消息，但不越过账号、会话和业务边界。乱序到达的回复先持久保留，原消息到达且完成分流后再排队；内部队列顺序保证原消息先处理。若规则版本已不同，需人工新建或选择明确的归并方式。

空闲超时、消息数量/上下文容量达到上限、人工结束，或 Multica 任务单处于 done/cancelled 时创建新一代任务。缺少 conversation_id/topic_id 时只为该消息建单，绝不把缺失标识的请求汇入公共任务。thread_id 也必须与当前归并键和账号完全一致。

## 队列与模型执行

接收事务先写入消息，再返回 202；来源、账号、消息 ID 唯一。相同 ID 相同内容返回原记录，不同内容返回 409。图片采用来源和账号范围内的内容寻址，重复上传获得相同图片 ID，便于安全重试整个请求。

规则按 priority 降序，规则 ID 升序匹配第一条。规则只决定目标及归并方式，模型由 Multica agent 自身配置。无匹配规则的消息保留为待分流；规则修改不会偷偷迁移已接收消息。人工重新排队未投递消息时会明确采用当前规则。

每个业务归并键同时最多投递一个批次。当前批次的对应模型执行未结束前，后续消息保留在本地队列；不会把新请求的结果误认为前一轮结果。其他业务会话可并行。短时间连续消息可以合批，每个消息仍有独立 ID 和独立结果记录，结果明确标记共享的 batch_id/task_id。

队列全局最多 20000 条非终态消息、单来源最多 5000 条；满时返回 429，生产者应保留原 ID 稍后重试。单条文字 16000 字、上下文 24KB、最多 6 张图片、每张 8MB/2000 万像素。工作台 SDK 对长业务字段截取并标记 context_truncated，聊天资料优先保留最近消息；不会把大段历史全部塞入一次请求。单批上下文最多 128KiB；任务上下文默认 256KiB，达到上限新建一代任务。优先级加入等待时间补偿，减少低优先级长期饥饿。

当前为单机 SQLite WAL 队列，一个 systemd 服务内两个 worker，最多 8 个待完成远程批次。事务认领与租约用于并发及重启恢复；不将 SQLite 文件跨服务器共享。扩容到多主机时应将存储、认领、租约和结果 outbox 一并迁移到支持事务的共享数据库或队列后端。

## 远程写入与不确定结果

Channel 无法替 Multica 提供跨服务原子事务，因此不宣称端到端 exactly-once。

创建任务或追加评论前，先持久记录批次 ID、写入阶段和意图；任务描述/评论带固定批次标记。收到响应后保存 issue_id/comment_id。超时、5xx、重定向或写入期间重启时，先从 Multica 查找原标记。找到后绑定原记录，不能确认则进入 uncertain 并暂停该业务会话。管理台可再次核对，不提供绕过检查的盲目重发按钮。

GET 和未开始远程写入的前置检查可重试。明确拒绝且未投递的请求可人工重新排队。模型失败不自动换 ID 重跑。模型超出等待时间进入 attention，继续低频查结果并阻塞该会话后续投递，避免旧任务还在运行时再次启动。

Multica 追加评论必须通过原任务的附件归属检查：已有任务图片上传携带 issue_id，再将附件绑定到评论。首次建单图片先上传为未绑定附件，建单时原子绑定。测试覆盖这两种契约。

## 输出与采用

首次请求匹配该任务单的初始 agent 执行；追加请求按 trigger_comment_id 或 Multica 的 coalesced/delivered/supplement 覆盖字段匹配执行。只读取已完成执行的最终结果，必要时从同一执行的 agent 评论或最终文本恢复，不返回 thinking/tool_result。

推荐模型返回 reply、summary、labels、requires_human；非 JSON 输出仍作为纯文本保留。模型输出不作为命令执行，浏览器按文本转义显示。Channel 提供按事件查询，以及按来源/账号的结果游标与显式确认；结果确认不会删除审计记录。

进入真实 agent 意味着使用它已有的模型、工具和运行权限。Channel 的业务指令要求只分析/起草，但这不是操作系统沙箱。不要给处理不可信平台数据的 agent 配置不必要的写入权限；权限应在 Multica 层治理。

## 后续业务扩展方向

主动提交、可配置分流、确定性归并和结果回传之外，现已增加[账号目标与动作编排](account-automation.md)：业务事件、目标 agent、沟通事项、受约束动作、账号领取与回执、跟进计时，以及默认关闭的闲鱼文字私信连接器。各平台自动订阅、跨平台客户主档、分类 agent 的两阶段分流和签名 webhook 推送仍需要独立实现；不能仅凭 Channel 连通就宣称八个平台自动收发已启用。
